# AGENTS.md

# Neighbourhood Bank — Administrator Bot

## 1. Project Overview

This project is a simple neighbourhood contribution/fund management system.

The system is **not a commercial banking system**. It is a community fund/financial ledger used to track recurring monthly contributions from neighbourhood members.

The administrator interface is a dedicated **Telegram Bot**.

The administrator bot communicates with a **Cloudflare Worker backend**, which reads and writes data in **Cloudflare D1 (SQLite)** and stores the payment QR image in **Cloudflare R2 object storage**.

### Architecture

```text
                         Telegram
                            │
              ┌─────────────┴─────────────┐
              │                           │
          User Bot                   Admin Bot
              │                           │
              └─────────────┬─────────────┘
                            │
                         Webhook
                            │
                            ▼
                  ┌─────────────────┐
                  │ Cloudflare      │
                  │ Worker          │
                  │                 │
                  │ worker.js       │
                  │ fetch handler   │
                  │ scheduled (cron)│
                  └────────┬────────┘
                           │
                    ┌────────┬────────┐
                    ▼        ▼
              Cloudflare D1  Cloudflare R2
              SQLite         (QR image)
```

The administrator bot is responsible for:

* Member management
* Contribution/payment recording
* Balance lookup
* Unpaid member tracking
* Reports
* Payment account / QR-code management
* Notifications
* System configuration
* Audit logging

# 2. Core Principles

The implementation MUST follow these principles.

## 2.1 Security First

The Telegram administrator bot controls financial records.

Never trust:

* Telegram usernames
* Telegram display names
* User-provided member IDs
* User-provided administrator roles
* Callback data without validation
* Client-provided permissions

Use the immutable Telegram numeric user ID for administrator authentication.

Every administrator request MUST be authorized before executing an operation.

---

## 2.2 Auditability

Every operation that changes financial or administrative data MUST generate an audit record.

Examples:

* Add member
* Disable member
* Record payment
* Correct payment
* Change monthly contribution
* Change bank account
* Change QR code
* Change administrator
* Change system settings

Never silently modify financial records.

---

## 2.3 Ledger Integrity

Financial transactions MUST be treated as immutable whenever possible.

Do not delete financial transactions.

If a transaction is incorrect:

```text
Incorrect transaction
        ↓
Create correction/reversal
        ↓
Create correct transaction
```

The original transaction must remain available in the audit/transaction history.

---

## 2.4 Least Privilege

Administrators must have roles and permissions.

Initial roles:

```text
SUPER_ADMIN
TREASURER
ADMIN
```

Do not give every administrator full access.

# 4. Cloudflare D1 Database

Use **one Cloudflare D1 (SQLite) database**.

Do NOT create one database table per member.

Use the following tables:

```text
config
admins
users
transactions
audit
bot_state
processed_updates
notifications
counters
```

The full schema lives in `schema.sql` (apply in Cloudflare D1 console or `wrangler d1 execute`).

IDs are human-readable strings generated by the in-worker `nextId()` (e.g. `NB-0001`, `TX-000001`, `AUD-000123`, `ADM-0002`) using an atomic upsert on `counters`.

Timestamps are ISO strings (TEXT); `bot_state.state` is a JSON string.

# 9. Individual Member Views

Every active member's transaction history is a filtered query over the central `transactions` table.

Example:

```text
SELECT * FROM transactions WHERE user_id = 'NB-0001' ORDER BY timestamp;
```

There is no separate per-member ledger table.

The central `transactions` table is the authoritative transaction ledger.

The per-member view is derived from it; the implementation MUST NOT write financial records anywhere other than `transactions` (and its `audit` entry) to avoid inconsistent records.

# 11. Cloudflare R2

The payment QR image is stored as the object `payment-qrcode.png` in the Cloudflare R2 bucket bound to the Worker as `QR_BUCKET`.

The QR code for the administrator's bank/payment account is stored there.

It is served publicly by the Worker at `GET /qr` (with `Cache-Control: public, max-age=3600`).

The public QR URL is stored in:

```text
config
```

under key:

```text
qr_url
```

Example:

```text
https://nb-admin.somesite.workers.dev/qr
```

Do not store large binary files in the database.

# 31. Concurrency

D1 provides ACID transactions per statement, and the Worker is single-threaded and handles one request at a time, so in-process operations are serialized.

Still, financial mutations must be protected against overlapping requests and Telegram webhook retries:

```text
Record payment
Correct payment
Create member
Update member
Change settings
```

Use a short in-worker mutex around read-modify-write financial flows:

```text
Acquire lock
    ↓
Validate data
    ↓
Read current balance
    ↓
Write transaction
    ↓
Write audit
    ↓
Release lock
```

Always release locks in error handling (`finally`).

Additionally, enforce uniqueness in the database as a backstop. `transactions.reference` has a partial unique index (only for non-null references), and `processed_updates.update_id` is a primary key — a second insert with the same `update_id` fails safely.

---

# 32. Idempotency

Payment operations must protect against duplicate submissions.

A Telegram callback or webhook may be delivered more than once.

Before creating a transaction, verify that the operation has not already been processed.

Use a unique:

```text
transaction_id
```

and, where appropriate:

```text
request_id
```

Never create duplicate financial transactions because Telegram retries a webhook.

As a backstop, the `processed_updates` table stores every `update_id` seen; re-delivered updates are skipped. `transactions.reference` additionally carries a partial unique index so a retried insert fails safely.

# 48. Deployment

Before production deployment:

1. Create the D1 database and apply `schema.sql` (D1 console or `wrangler d1 execute`).
2. Bind the D1 database as `DB` and create the R2 bucket bound as `QR_BUCKET`.
3. Create the Cloudflare Worker and paste `worker.js`.
4. Set environment variables and secrets (`BOT_TOKEN`, `WEBHOOK_SECRET`; optional `TIMEZONE`, `QR_PUBLIC_URL`).
5. Create the Telegram admin bot (via BotFather).
6. Configure the Telegram webhook to the Worker URL with `secret_token`.
7. Create initial SUPER_ADMIN.
8. Verify webhook.
9. Test authentication.
10. Test payment recording.
11. Test audit logging.
12. Test QR code display/update.
13. Test notifications.
14. Test backup/recovery procedure.


```text

        ↓
```


# 52. Important Implementation Rule

Do not over-engineer this project.

The initial target is a small neighbourhood community.

Prefer:

```text
Simple
Reliable
Auditable
Secure
Easy to operate
```

over:

```text
Complex
Highly distributed
Infrastructure-heavy
```

Cloudflare Worker + D1 (SQLite) + Cloudflare R2 + Telegram is intentional for v1.

The Worker is a single file that can be pasted directly in the Cloudflare dashboard; the data layer is standard SQLite, so business logic stays portable.
